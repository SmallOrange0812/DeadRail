2인 협업 워크플로우 (매일 반복하는 사이클)
메인(main) 브랜치는 언제든 실행 가능한 '안전한 완성본'이어야 합니다. 두 분은 절대 main 브랜치에서 직접 작업하지 않습니다.

최신화 (Pull): 작업 시작 전, 항상 main 브랜치로 이동하여 최신 버전을 Fetch/Pull 받습니다.

브랜치 생성 (Branch): 오늘 작업할 기능의 이름으로 새 브랜치를 만듭니다. (예: feature/P1-hacking-ui, feature/treadmill-move)

개발 및 커밋 (Commit): 유니티에서 열심히 작업한 뒤, 변경된 파일들을 커밋합니다. 이때 기능 단위로 잘게 쪼개서 자주 커밋하는 것이 좋습니다.

푸시 (Push): 작업이 완료되면 브랜치를 서버로 푸시합니다.

병합 요청 (Pull Request): GitHub 웹사이트로 가서 main 브랜치로 코드를 합쳐달라는 PR을 생성합니다. 이때 다른 개발자가 코드를 리뷰하고, 문제가 없으면 Merge 버튼을 눌러 main에 합칩니다.

다시 1번으로 돌아가 기존 작업 브랜치는 지우고, 최신화된 main에서 새 브랜치를 파서 다음 작업을 시작합니다.


유니티 협업 시 절대 엄수해야 할 3가지 규칙
이 규칙을 어기면 프로젝트가 망가지고 복구하는 데 며칠이 소요될 수 있습니다.

규칙 1: .meta 파일은 영혼의 단짝이다.
유니티는 이미지나 스크립트를 생성할 때마다 보이지 않는 짝꿍인 .meta 파일을 만듭니다. (예: Player.cs 생성 시 Player.cs.meta 자동 생성).
GitHub Desktop에서 커밋할 때, 원본 파일은 체크하고 .meta 파일은 체크 해제하는 실수를 절대 하지 마세요. 두 파일은 무조건 세트로 커밋되어야 유니티 연결(Reference)이 끊어지지 않습니다.

규칙 2: 같은 씬(Scene)을 동시에 열고 작업하지 않는다.
유니티의 씬 파일(.unity)은 텍스트로 이루어져 있지만 구조가 매우 복잡합니다. 두 사람이 같은 씬을 건드리면 100% 충돌이 나며 병합이 불가능에 가깝습니다.
개발자 A용 테스트 씬, 개발자 B용 테스트 씬을 아예 따로 만들어서 그 안에서만 작업하세요.

규칙 3: 메인 씬 통합은 오직 '프리팹(Prefab)'으로만 한다.
기능 개발이 끝났다면, 개발자 B는 완성된 몬스터나 배경을 Prefab 폴더에 드래그하여 프리팹(.prefab)으로 만듭니다. 그리고 PR을 통해 코드를 합칩니다.
메인 씬 관리를 담당하는 사람(예: 개발자 A)은 변경된 씬을 가져오는 것이 아니라, main 브랜치에 올라온 '몬스터 프리팹'을 마우스로 끌어다가 메인 씬에 올려놓기만 해야 합니다.
